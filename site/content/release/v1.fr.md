**Brouillon** — Cette page n’est pas publiée : le fondateur la relit d’abord. Krizaka Agents est notre propre système d’ingénierie, privé, utilisé chaque jour en interne ; il n’y a rien à acheter ni à demander ici, et aucune date n’est promise.

La page compagnon liste chaque [variable d’environnement renommée](/fr/migration/).

### § 1 — Qui il sert et ce qu’il atteint

Krizaka Agents entoure les sessions de code pour qu’un ticket devienne une pull request vérifiée et fusionnée. Chaque schéma de cette page est disposé depuis le modèle d’architecture du système lui-même, jamais dessiné à la main : quand le modèle change, le dessin change avec lui.

<!--release-view:v1_c1-->

### § 2 — Le cœur parle aux ports

Les parties qui décident (le constructeur de sessions, les commandes, les trains, le coordinateur, le watchdog) dépendent d’interfaces, pas d’un fournisseur. Un réglage manquant ou inconnu arrête le démarrage au lieu d’apparaître plus tard.

<!--release-view:v1_c2-->

Chaque interface a un adaptateur, et c’est dans l’adaptateur que vit le nom d’un fournisseur.

<!--release-view:v1_adapters-->

### § 3 — La tour

Ce qui surveille le travail : les lanceurs automatiques, le watchdog, la rotation des identifiants, le service d’opérations et le cockpit local. Un modèle ne décide jamais de la clôture d’une alerte.

<!--release-view:v1_tower-->

### § 4 — Un seul format d’événement, un seul puits

Le constructeur de sessions, les commandes et les trains écrivent un seul format d’événement, à un seul endroit, qui sort en journaux OpenTelemetry.

### § 6 — L’environnement, renommé

Les réglages sont nommés par le rôle qu’ils servent, pas par l’organisation ni par le fournisseur derrière eux. Pendant une version, un ancien nom passe encore par la table d’alias avec un avertissement qui donne le nouveau ; ensuite, l’ancien nom est refusé.

La [page de migration](/fr/migration/) liste chaque ancien nom et le nouveau.
